# تحلیل RFM مشتریان


## معرفی پروژه

این پروژه با هدف **تحلیل رفتار خرید مشتریان** و طراحی یک مدل بخش‌بندی مبتنی بر چارچوب **RFM** روی داده‌های فروش پایگاه داده `AdventureWorks` توسعه یافته است.

در کنار تحلیل مشتریان، عملکرد دو رویکرد متفاوت SQL ارزیابی شد تا مشخص شود آیا اتصال جدول سفارش‌ها به جدول جزئیات سفارش برای محاسبه شاخص‌های RFM ضروری است یا می‌توان همان نتیجه را با کوئری ساده‌تر و منابع پردازشی کمتر به دست آورد.

## مسئله کسب‌وکار

رفتار و ارزش مشتریان یکسان نیست. برخی مشتریان اخیراً خرید کرده‌اند، برخی دفعات خرید بیشتری دارند و گروهی نیز درآمد بالاتری برای کسب‌وکار ایجاد می‌کنند.

در این پروژه، مشتریان بر اساس سه شاخص اصلی ارزیابی شدند:

| شاخص | مفهوم | پرسش کسب‌وکار |
|---|---|---|
| **Recency** | فاصله زمانی از آخرین خرید | مشتری چه مدت پیش خرید کرده است؟ |
| **Frequency** | تعداد دفعات خرید | مشتری چند بار خرید کرده است؟ |
| **Monetary** | مجموع ارزش خرید | مشتری چه میزان درآمد ایجاد کرده است؟ |

خروجی این تحلیل می‌تواند برای شناسایی مشتریان وفادار، مشتریان در معرض ریزش، مشتریان کم‌ارزش و مشتریان دارای پتانسیل رشد استفاده شود.

## رویکرد تحلیلی

فرایند اجرای پروژه شامل مراحل زیر بود:

1. استخراج داده‌های سفارش از پایگاه داده `AdventureWorks`
2. محاسبه شاخص‌های `Recency`، `Frequency` و `Monetary`
3. مقایسه دو روش پیاده‌سازی، با و بدون `JOIN`
4. ارزیابی عملکرد کوئری‌ها با معیارهای اجرایی SQL Server
5. امتیازدهی مشتریان با توابع پنجره‌ای
6. آماده‌سازی خروجی برای بخش‌بندی و تحلیل بازاریابی

## بهینه‌سازی کوئری SQL

دو رویکرد برای استخراج داده‌های موردنیاز مقایسه شدند:

- استفاده مستقیم از جدول `SalesOrderHeader`
- اتصال `SalesOrderHeader` به `SalesOrderDetail`

هر دو روش خروجی تحلیلی یکسانی تولید کردند، اما حذف `JOIN` غیرضروری باعث کاهش محسوس خوانش داده و زمان پردازش شد.

| معیار عملکرد | بدون `JOIN` | با `JOIN` |
|---|---:|---:|
| Logical Reads | 686 | 1,238 |
| CPU Time | 78 ms | 328 ms |
| Execution Time | 56 ms | 379 ms |
| Output Rows | 19,119 | 19,119 |

### نتیجه بهینه‌سازی

رویکرد بدون `JOIN`:

- حدود **1.8 برابر Logical Read کمتر**
- حدود **4.2 برابر زمان CPU کمتر**
- حدود **6.7 برابر زمان اجرای کمتر**
- جلوگیری از پردازش اضافی و ایجاد رکوردهای تکراری
- حفظ کامل خروجی موردنیاز برای تحلیل RFM

این نتیجه نشان می‌دهد زمانی که اطلاعات تجمیعی موردنیاز در سطح سفارش موجود است، استفاده از جدول جزئیات صرفاً هزینه پردازشی کوئری را افزایش می‌دهد و ارزش تحلیلی جدیدی ایجاد نمی‌کند.

> Performance results are based on the execution measurements documented in the project report.

## امتیازدهی مشتریان

برای رتبه‌بندی و امتیازدهی مشتریان از توابع تحلیلی SQL استفاده شد:

### `NTILE(4)`

این تابع مشتریان را بر اساس هر شاخص به چهار گروه تقریباً هم‌اندازه تقسیم می‌کند و برای ایجاد امتیازهای چهارسطحی RFM مناسب است.

### `CUME_DIST`

این تابع جایگاه نسبی هر مشتری را در توزیع داده‌ها مشخص می‌کند. استفاده از آن برای شاخص `Monetary` مفید است؛ زیرا ارزش خرید مشتریان معمولاً دارای توزیعی نامتقارن و مقادیر پرت است.

در طراحی امتیازها، جهت شاخص‌ها نیز در نظر گرفته شد:

- **Recency کمتر** به معنای عملکرد بهتر مشتری است.
- **Frequency بیشتر** به معنای تعامل و تکرار خرید بیشتر است.
- **Monetary بیشتر** نشان‌دهنده ارزش مالی بالاتر مشتری است.
